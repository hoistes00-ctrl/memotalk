# Windows Markdown 저장 진단 및 Sync 기반 검증

2026-11-11, `feature/obsidian-bridge-prototype`. main 병합·배포·실사용 데이터 변경 없음.

## 확인한 사실과 미확인 원인

- 지정한 `shared/index.html`, `windows/main.js`, `shared/platform-bridge.js`를 분석했다.
- 실제 대상 폴더를 읽기 전용으로 조사했을 때 파일 123개, 0바이트 Markdown 1개, 인덱스 없음이었다. 기존 파일/폴더를 수정·삭제하지 않았다. 개인 경로·제목·내용은 이 저장소에 기록하지 않는다.
- 관측된 파일의 최대 전체 경로는 172자였다. 이전 임시 이름의 접미사까지 더해도 일반적인 260자 경계 이내다. 이 자료만으로 경로 길이를 원인으로 확정할 수 없다.
- 기존 코드에는 `touch → 임시 파일 쓰기 → rename → 마지막에 인덱스 저장` 순서가 있다. rename 등이 실패하면 0바이트 파일이 남을 수 있고, 다음 실행은 인덱스 없는 비어 있지 않은 폴더를 거부한다. 이는 코드와 실패 테스트로 검증한 결함이다.
- Electron `invoke()`에서 던진 오류의 사용자 정의 필드가 전달되지 않는 문제를 피하기 위해 성공/실패 응답을 JSON 호환 envelope로 바꿨다. 브리지에서 코드·errno·syscall·단계·상대 경로·임시/대상 경로를 복원한다.
- Windows Defender 이벤트 1123에서 현재 개발 도구의 문서 폴더 접근 차단을 확인했다. 메모톡의 과거 vault 실패와 연결되는 차단 이벤트는 찾지 못했다. 개발 체크아웃은 쓰기 가능한 별도 로컬 작업 폴더에서 수행했다. 보안 설정은 변경하지 않았다.
- 실제 실패 당시의 네이티브 오류 로그는 남아 있지 않아 **과거 최초 실패의 오류 코드와 원인은 아직 미확정**이다. 0바이트 파일은 조사 대상이며, 그 파일이 최초 실패였다고 단정하지 않는다.
- 별도 프로세스가 합성 Markdown을 잠그는 실제 Windows 시험에서 **`EPERM / rename / commit`**을 재현했다. 기존 내용 보존을 확인했다. 이는 수정 동작의 검증이며 과거 vault 원인 확정은 아니다.
- Obsidian Sync 비밀번호는 원격 암호화에 사용된다. 공식 Sync는 로컬 vault를 암호화하지 않으므로 비밀번호만으로 로컬 파일 쓰기 실패를 설명할 수 없다. 별도 암호화 플러그인/OS 암호화는 별도 조사 대상이다.

## 구현된 저장 및 복구 정책

1. 폴더 연결에 세대 토큰을 부여한다. 다른 창에서 폴더를 바꾸면 오래된 핸들은 `ESTALE`로 거부한다. Windows 저장 중에는 해당 창의 lease로 다른 창 저장과 폴더 변경을 막는다.
2. 전체 출력과 기존 인덱스/미완료 작업 기록을 비교한다. 외부 수정·추적된 파일 누락·경로 탈출·Windows 대소문자 충돌이면 쓰기 전에 중단한다. 기존 CRC 인덱스는 그 값과 일치할 때만 SHA-256 기록으로 전환한다.
3. `.memotalk-file-journal.json`을 먼저 쓰고 다시 읽어 검증한다. 미완료 기록은 같은 연결에서 재시도할 수 있다. 잘못된 기록이나 다른 연결 ID는 채택하지 않는다.
4. 새 Windows 파일은 `touch`로 미리 만들지 않는다. 짧은 임시 이름으로 쓰고 flush/바이트 검증 후 hard link로 배타 게시한다. 기존 파일은 기준 바이트를 재확인하고, 검증된 `.memotalk-history/<transaction-id>/...` 사본을 남긴 후 갱신한다. 실패 시 자동 재시도로 외부 파일을 덮어쓰지 않는다.
5. Markdown·첨부를 먼저, manifest를 다음, 일반 Sync descriptor를 마지막에 쓴다. 변경하지 않은 파일까지 모두 다시 읽어 검증하고 로컬 인덱스를 최종 기록·읽기 검증한다.
6. 불필요해진 경로도 삭제하지 않고 계속 추적한다. 자동 정리·삭제 전파는 이번 범위에 없다.
7. 인덱스/작업 기록이 없는 이전 불완전 저장본은 비교 결과(일치/누락/다름/빈 파일 수)를 보여 준다. 사용자가 새 빈 폴더를 고르면 **현재 앱 내부 데이터**로 새 저장본을 만든다. 기존 폴더의 다른 내용·추가 파일은 원본에 남고 가져오지 않는다. 손상된 인덱스도 새 폴더 복구 대상으로 검사할 수 있다.
8. 저장 오류는 로컬 진단 메뉴와 localStorage에만 기록한다. 경로에 개인 정보가 포함될 수 있으므로 공개 PR에 붙이지 않는다. 재시작 시 연결 복원만으로 저장 완료를 표시하지 않는다.
9. 자동 저장 간격은 0..2147483647ms 전체 타이머 범위의 숫자 입력, 현재 값 표시, 기본값 복귀, 즉시 적용, localStorage 영속화를 제공한다. 기본 1400ms.

## Obsidian Sync 전달 규약

Obsidian Sync는 `.obsidian` 설정 폴더를 제외하면 점으로 시작하는 일반 파일/폴더를 전송하지 않는다. 로컬 인덱스·journal·history는 **기기 로컬 기록**이며 원격 전달을 전제로 하지 않는다.

`memotalk-sync-state.json`은 숨김 파일이 아닌 검증 descriptor다. 각 출력의 SHA-256과 정렬된 파일 해시 목록으로 만든 snapshot ID를 담는다. 자신과 로컬 dotfile은 목록에 포함하지 않는다. 수신 측 `verifySnapshot()`은 descriptor와 각 파일의 해시, 읽기 전후 descriptor 동일성을 확인한다. 누락·변경·전송 순서 뒤바뀜은 `mirror_remote_pending`으로 보류한다. 읽기 전용 검사이며 내부 메모를 변경하지 않는다.

각 기기의 Obsidian에서 전용 폴더가 제외되지 않았는지 확인하고 `Sync all other types`를 켜야 JSON descriptor와 manifest를 전송할 수 있다. 사진/첨부 유형과 실제 플랜의 파일 크기 제한도 확인해야 한다. 앱의 로컬 성공은 원격 업로드 완료가 아니며, 실제 원격 전송은 Obsidian 상태와 두 번째 기기의 완결성 검사로 확인한다.

공식 문서: [암호화 및 로컬 파일](https://help.obsidian.md/Obsidian%20Sync/Security%20and%20privacy), [선택 동기화와 숨김 파일 제외](https://obsidian.md/help/sync/settings).

## 남은 위험과 후속 순서

- 과거 최초 실패 코드: 기존 vault는 보존하고 개발 버전을 별도 프로필과 새 시험 하위 폴더로 실행하여 재현해야 한다. 진단의 `relativePath/code/errno/syscall/operation`을 확인한 후 잠금·권한·보안 프로그램을 구분한다. 비밀번호 수집이나 Defender 전체 해제는 필요하지 않다.
- Node의 기존 파일 비교와 rename 사이에는 외부 프로세스와의 경쟁 구간이 있다. 앱 내부 여러 창은 lease로 막지만 외부 편집기/Sync를 완전히 잠그지 못한다. 현 단계에서는 메모톡이 쓰는 폴더를 단일 작성자로 운용하고 Obsidian에서는 읽기만 한다. 완전한 양방향 전환 전 불변 revision 파일과 적용 로그 설계가 필요하다.
- 새 파일의 hard-link 게시가 지원되지 않는 파일시스템/네트워크 드라이브는 안전하게 실패한다. NTFS 임시 폴더에서 검증했고 모든 저장 매체를 보장하지 않는다. 중단된 임시 파일은 자동 삭제 대상으로 넓게 탐색하지 않는다.
- flush 이후에도 전원 단절/디스크 손상에 대한 완전한 내구성 보장은 아니다. 검증 실패를 성공으로 표시하지 않으며, 읽을 수 없는 metadata는 원본을 보존하고 새 폴더 복구로 처리한다.
- 이력 사본과 이전 경로는 용량을 차지한다. 삭제·보관 기간 정책과 사용자 승인 UI는 후속 단계다. 로컬 history는 Sync 백업이 아니다.
- Android는 공유 UI/브리지를 동일하게 유지했으나 기존 SAF 쓰기는 Windows와 같은 원자적 교체/flush 보장이 없다. Android 자동 쓰기를 안정화됐다고 간주하지 않는다.

다음 구현은 (1) 두 기기 합성 파일 단방향 전송, (2) Android SAF 권한 유지와 읽기 전용 snapshot 검증, (3) 가져오기/충돌 미리보기, (4) 메모 ID 기반 revision·operation ID·tombstone과 불변 첨부 해시, (5) 오프라인/동시 수정/삭제/복원/이동 검증 순으로 한다. 단순 파일 부재를 삭제로 해석하거나 기기 시각만으로 충돌 승자를 고르지 않는다. 초기 연결은 합집합 미리보기 후 적용하며 기존 데이터는 별도 승인 없이 덮어쓰지 않는다.
